# Module I18n

Modules can ship their own translations. Messages are **namespaced** under
`mod.<moduleId>.*` so they never collide with core strings.

## File structure

Each module can provide translations as JSON files:

```
modules/<moduleId>/i18n/<area>/<locale>.json
```

For prebuilt modules, use:

```
modules/<moduleId>/dist/i18n/<area>/<locale>.json
```

Supported areas:

- `global`
- `dashboard`
- `admin`
- `login`

The generator reads `modules/<moduleId>/module.json` to resolve the `moduleId`.

Locales are detected from the JSON filenames, so you can add any locale without
changing the host config. The host will fall back to `DEFAULT_LOCALE` if a
locale is missing from core messages.

## Namespacing

All module strings must be nested under the module id:

```json
{
  "title": "Analytics",
  "nav": {
    "overview": "Overview"
  }
}
```

This is stored internally as:

```
messages.mod["mod.analytics"].title
```

## Build step

Run the generator to build the registry:

```
pnpm modules:i18n
```

This writes:

```
lib/i18n/messages/modules.generated.ts
```

The runtime merges these into `messagesByArea`, so `useAreaMessages` and
`getServerMessages` include module strings under `messages.mod[...]`.

Combine with `pnpm modules:prepare` to ensure the module registry is also
generated before build.

Module discovery uses:

1. `MODULES_DIR` env var (optional)
2. `/modules` (default)
3. `/examplemodules` (fallback for samples)

## Example usage

```tsx
import { useAreaMessages } from '@/lib/i18n/client';

export function AnalyticsHeader() {
  const messages = useAreaMessages('admin');
  const mod = messages.mod['mod.analytics'];
  return <h1>{mod.title}</h1>;
}
```
