# Module I18n

For new module and theme UI, the default path is the SDK flat translator:

- `useI18n()` in React components
- `createTranslator()` in plain TypeScript utilities or tests
- `t('Hello')` style lookups using English source strings as keys

The older structured module message tree still exists, but it is a secondary
contract for host-side typed trees. For most new module and theme UI, prefer
the flat translator.

## 1. SDK quick start

`useI18n()` returns a translator function:

```tsx
import { useI18n } from '@skitsaas/sdk';

export function SaveButton() {
  const t = useI18n();
  return <button>{t('Save')}</button>;
}
```

That means usage is exactly:

```ts
const t = useI18n();
t('Hello');
```

Behavior:

- if the current locale has a translation, it returns it
- otherwise it falls back to the default locale
- if no translation exists, it returns the original key such as `'Hello'`

For non-React code, use `createTranslator()`:

```ts
import { createTranslator } from '@skitsaas/sdk';

const t = createTranslator('es', {
  translationsByLocale: {
    es: {
      Hello: 'Hola'
    }
  }
});

t('Hello'); // "Hola"
```

## 2. Modules

### Preferred module contract: flat translations

For most module UI, store flat translations here:

```text
modules/<moduleId>/i18n/translations/<locale>.json
```

Compiled/prebuilt modules should emit:

```text
modules/<moduleId>/dist/i18n/translations/<locale>.json
```

Example:

```json
{
  "Hello": "Hola",
  "Save": "Guardar",
  "Settings saved": "Configuracion guardada"
}
```

Example module component:

```tsx
import { useI18n } from '@skitsaas/sdk';

export function ModuleToolbar() {
  const t = useI18n({ moduleId: 'mod.analytics' });

  return (
    <div>
      <h2>{t('Hello')}</h2>
      <button>{t('Save')}</button>
    </div>
  );
}
```

Rules:

- keys are English source strings
- values are translated strings
- files must be flat JSON objects; nested objects are invalid
- module flat translations are locale-scoped, not area-scoped
- `useI18n({ moduleId })` resolves module-local flat translations before the
  shared flat registry
- if `dist/i18n/translations` exists, the host reads `dist` and ignores source
  files for that module
- if two sources define the same `locale + key` with different values,
  `pnpm i18n:prepare` fails

### Optional module contract: nested area messages

Use nested area messages only when the module needs a structured tree mounted
under:

```text
messages.mod["mod.<moduleId>"]
```

Source layout:

```text
modules/<moduleId>/i18n/<area>/<locale>.json
```

Compiled/prebuilt layout:

```text
modules/<moduleId>/dist/i18n/<area>/<locale>.json
```

Supported areas:

- `global`
- `dashboard`
- `admin`
- `login`

Example:

```json
{
  "title": "Analytics",
  "nav": {
    "overview": "Overview"
  }
}
```

This contract is mainly for host-side typed access through
`getAreaMessages()` / `useAreaMessages()`. It is not the primary SDK-first path
for new module UI.

Host-side example:

```tsx
import { useAreaMessages } from '@/lib/i18n/client';

export function AnalyticsHeader() {
  const messages = useAreaMessages('admin');
  const mod = messages.mod['mod.analytics'];
  return <h1>{mod.title}</h1>;
}
```

## 3. Themes

Themes use the same SDK hook, but their files live in a different directory
shape.

Theme translation files:

```text
themes/<themeId>/locales/<area>/<locale>.json
```

Example theme component:

```tsx
import { useI18n } from '@skitsaas/sdk';

export function ThemeActionLabel({ themeId }: { themeId?: string }) {
  const t = useI18n({ themeId, area: 'admin' });
  return <span>{t('Cancel')}</span>;
}
```

Theme notes:

- themes use `locales/`
- modules use `i18n/`
- themes are area-scoped
- `global` theme translations merge before the requested area
- if a theme does not override a key, it falls back to the core flat registry

## 4. Naming rules that usually cause confusion

- `useI18n()` is the runtime API, not a folder naming rule
- modules do not move to `modules/<moduleId>/locales`
- themes do use `themes/<themeId>/locales`
- module flat translations and theme flat translations both end up consumed by
  the same translator pattern: `const t = useI18n(); t('Hello')`

## 5. Locale behavior

Locales are inferred from JSON filenames, so modules and themes can add locale
files without editing host TypeScript imports.

Core locales still provide the default typed host trees, but the host can now
publish extra locales without adding `lib/i18n/locales/<locale>/*`.

Ways to extend the language switcher:

- add core locale folders under `lib/i18n/locales/*`
- declare `additionalLocales` in `themes/<themeId>/config.ts`
- declare `additionalLocales` in `ModuleManifest`
- add module flat translation files under `i18n/translations/<locale>.json`

Behavior:

- `SUPPORTED_LOCALES` is generated from the union of those sources
- if a locale has no typed core bundle, `useAreaMessages(...)` falls back to
  the default locale (`en`)
- `useI18n({ moduleId })` checks the module bucket first, then the shared flat
  registry, then the default locale, then the raw key
- flat translators still use any theme/module translations that exist for the
  selected locale
- if no translation exists anywhere, the translator returns the original
  English key

## 6. Build order

Use this order when module i18n changes:

1. `pnpm modules:build`
2. `pnpm modules:prepare`
3. `pnpm modules:i18n`
4. `pnpm i18n:prepare`

Notes:

- `modules:i18n` rebuilds the nested module tree
- `i18n:prepare` rebuilds the flat translation registry, including module flat
  files and extended supported locales
- theme flat translations are prepared by `pnpm themes:prepare`
